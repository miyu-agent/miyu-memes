# M-14 后台页：列表给小图、原图分块取

2026-11-11。

## 一、为什么

项目主人报后台页的图全是灰块。查到两个原因，这一步修包这一头的那一个；另一个在核心，已另修。

- 后台页列表里每张图都调页面方法 `image {id}`：包把整张原图从核心分块 `blob.get` 读回来，拼成一整段 base64 放进一条回应。
- 核心收一行最多 1 MiB。原图大于约 750 KB 的，这条回应被核心拒掉：新版核心让这次调用当场失败，旧版会一直挂着，把页面卡死。
- 主人的库 351 张里 53 张超过 700 KB。
- 列表一屏几十张都取原图，本身就慢。
- 取不到的格子原来只加一个没有样式的 `is-broken`，看上去就是灰块，分不出是没到还是坏了。

## 二、怎么改

### 1. 小图：新页面方法 `thumb {id}` → `{media_type, data}`

- 长边不超过 256 像素（`src/thumb.rs`）。
  - 不透明的编成 JPEG（质量 80）；有透明的编成无损 WebP（`image` 库的 WebP 只能编无损，比 PNG 小）。
  - 动图（GIF、WebP、APNG）取第一帧。
  - 本来就在 256 以内、不是动图、字节也不超的，原样回，一个字节不动。
- 回应远小于一行 1 MiB：小图最多 192 KiB（base64 是 256 KiB）。超了的先把 JPEG 质量降到 60，再把长边每次缩到四分之三，到 64 像素还装不下的回 `thumb_too_big`；解不开的回 `not_image`。
- 缓存在包的状态目录里：库 `library.db` 旁边的 `thumbs/`，文件名是图的哈希（`sha256:` 后面那 64 位十六进制），没有扩展名，类型读的时候照内容认。
  - 第一次要时读原图现做（原图照旧分块 `blob.get`），以后直接读缓存，不再问核心。
  - 缓存认不出来、读不了的当没有，重做。
  - 先写临时文件再改名：读的一方见不到写了一半的。
  - 哈希不是那个样子的不落盘（文件名带不进别的路径）。
- 删了表情，小图跟着删：`Library::purge` 是真删的唯一一处（后台页删、内容包拿掉都走它），在那里删。停用不删。

### 2. 原图分块：`image {id, offset?}` → `{media_type, data, size, next?}`

- `offset` 是字节，不写是 0；不是非负整数的回 `-32602`。
- 一次最多回 384 KiB 原始字节（base64 是 512 KiB，一行 1 MiB 的余量留足）。
- `size` 是整张的字节数；后面还有的带 `next`（下一次的 `offset`），到头的没有。
- 块的边界是 3 的倍数：每块的 base64 没有补位（最后一块除外），各块接起来就是整张的 base64。
- 不带 `offset`、图又小于一块的，回应和原来一样，多一格 `size`。
- 包不再把整张拼在一条回应里：一次调用只向核心读要的那一块。

### 3. 后台页前端（`package/page/`）

- 列表（`grid.js`）改用 `thumb`；详情的大图（`detail.js`）照 `next` 循环取 `image`，各块解开接成一个 Blob（`images.js`）。
- 同时取图的并发照旧是 4，小图、原图合着算。
- 取不到的显示「加载失败」（三种语言，`texts.js` 的 `image_failed`），叠在格子、大图框的中间；一张失败不拦别的。失败的不记，下次要时重取。

### 4. 登记

- `package.methods` 多登记 `thumb`（`src/methods.rs` 的 `NAMES`）。清单的 `[export]` 只列给别的软件调的（`add`、`search`），`thumb` 是后台页自己用的，不加。
- 给模型看的字没动，登记簿不动。

## 三、验收

自动的：

- `cargo test`：
  - `thumb/tests.rs`：大图缩成 256 以内的 JPEG、比例不变；有透明的留着透明，256 见方装不下的再缩一档；小的静态图原样；动图不管大小都取第一帧；不是图的拒；缓存存、读、删；缓存文件坏了、空了的当没有；不像哈希的不落盘。
  - `methods/images/tests.rs`：原图两块以上接起来和整张的 base64 一字不差，`size`、`next` 对，每条回应都在一行以内，一次只读一块；小图不带 `offset` 和原来一样多一格 `size`；小图回应在限内、缓存命中时不再读原图；缓存坏了重做；原图坏的回 `not_image`。
  - `methods/tests.rs`：经 `method.call` 取小图、分块取原图，`offset` 写错的拒；真删以后缓存的小图没了；`thumb` 登记上了。
- 先红：只写了测试、实现还是老样子时这几组 13 条报红。
- `cargo clippy --all-targets --locked -- -D warnings`、`cargo fmt --check`、`cargo doc`（`RUSTDOCFLAGS=-D warnings`）、每个 `.rs` 不超过 500 行。

要人看的（前端没有自动测试，这一步没在浏览器里实测）：

1. 装上这一版，打开表情包后台页：列表每一格都出图，滚动时新进视口的陆续出来，没有一直灰着的格子。
2. 点开一张大于 750 KB 的（主人的库里有 53 张）：详情里的大图出来，动图照样会动。
3. 包的状态目录里多出 `thumbs/`，里面的文件名是 64 位十六进制；再开一次页面，列表明显比第一次快。
4. 彻底删除一张：`thumbs/` 里它那一个文件没了。
5. 把 `thumbs/` 里某个文件改成乱写的内容，重开页面：那一格照样出图，文件换回好的。
